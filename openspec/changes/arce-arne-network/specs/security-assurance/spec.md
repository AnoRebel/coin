# Spec Delta

## Purpose

Defines the security posture required before ARNE carries real value: a maintained threat model, secure defaults, supply-chain integrity, continuous fuzzing and testing, independent audits, coordinated disclosure, and incident response.

## ADDED Requirements

### Requirement: A living threat model covers every trust boundary

The project SHALL maintain a documented threat model covering keys, consensus, mempool, P2P, storage, APIs, contracts, bridges, confidential transfers, compliance data, and operators. Each identified threat MUST have a mitigation, owner, and test or control reference. The model MUST be reviewed at every major release.

#### Scenario: Threat has mitigation
- **WHEN** a threat is added to the model
- **THEN** it is linked to a mitigation and a verification method

#### Scenario: Release review
- **WHEN** a major release is prepared
- **THEN** the threat model review is completed and recorded

#### Scenario: New component
- **WHEN** a new externally reachable component is added
- **THEN** the threat model is updated before the component is enabled in production

### Requirement: Secure defaults are enforced

Production configurations MUST enable TLS, authentication, least-privilege scopes, encrypted storage, rate limits, and audit logging by default. The system MUST NOT ship default passwords, default keys, or permissive CORS.

#### Scenario: Default deployment is safe
- **WHEN** an operator deploys the production profile without customizing security settings
- **THEN** TLS, authentication, rate limits, and audit logging are enabled

#### Scenario: Default credentials rejected
- **WHEN** a deployment uses a published default credential
- **THEN** startup fails with a clear error

#### Scenario: Permissive CORS rejected
- **WHEN** a production configuration allows wildcard CORS with credentials
- **THEN** startup rejects the configuration

### Requirement: Releases are signed, reproducible, and inventoried

Every release SHALL include signed artifacts, checksums, a software bill of materials, and reproducible build instructions. Consumers MUST be able to verify the artifact signature and the SBOM MUST list direct and transitive dependencies with licenses.

#### Scenario: Verify a release
- **WHEN** a user downloads a release
- **THEN** they can verify its signature and checksum against the published key

#### Scenario: Reproducible build
- **WHEN** a builder follows the published instructions
- **THEN** the resulting binary or package matches the release hash

#### Scenario: SBOM completeness
- **WHEN** the SBOM is scanned
- **THEN** every shipped dependency appears with a version and license

### Requirement: Dependencies are pinned, scanned, and patched

The project SHALL pin dependencies with lockfiles, scan for known vulnerabilities in CI, and define response times by severity. A critical vulnerability MUST block release until patched or explicitly risk-accepted with an expiry.

#### Scenario: Vulnerability blocks release
- **WHEN** a critical vulnerability is found in a shipped dependency
- **THEN** the release is blocked until patched or risk-accepted

#### Scenario: Lockfile integrity
- **WHEN** a dependency is installed in CI
- **THEN** the lockfile hash is verified

#### Scenario: Patch SLA
- **WHEN** a high-severity advisory is published
- **THEN** a patch is released within the documented SLA

### Requirement: Security-critical code is continuously fuzzed and property-tested

Parsers, canonical encoders, signature verification, consensus state transitions, mempool admission, confidential proofs, and contract execution SHALL have continuous fuzzing and property-based tests. A crash, panic, or invariant violation MUST fail CI.

#### Scenario: Parser fuzzing
- **WHEN** a malformed message is generated by the fuzzer
- **THEN** the parser returns a typed error and does not panic

#### Scenario: State invariant
- **WHEN** a randomized sequence of valid and invalid transactions is applied
- **THEN** supply conservation and non-negative balances hold or the test fails

#### Scenario: Cross-implementation differential fuzzing
- **WHEN** the same random input is applied to the Go and Python implementations
- **THEN** both return the same result or the difference is recorded as a bug

### Requirement: Independent audits gate mainnet value

Before mainnet carries material value, the consensus, cryptography, confidential pool, bridge, contract runtime, and compliance flows SHALL receive independent security audits. Critical and high findings MUST be fixed and re-tested before launch.

#### Scenario: Audit completion
- **WHEN** an audit reports a critical finding
- **THEN** mainnet launch is blocked until the finding is fixed and verified

#### Scenario: Audit scope
- **WHEN** the audit is commissioned
- **THEN** its scope covers every component listed in the requirement

#### Scenario: Public report
- **WHEN** an audit is completed
- **THEN** a public report or summary is published with remediation status

### Requirement: Coordinated disclosure and bug bounty are operated

The project SHALL publish a security policy, a private disclosure channel, response timelines, and a bug bounty with clear scope and rewards. Researchers MUST receive a response within the published window.

#### Scenario: Report acknowledged
- **WHEN** a researcher submits a vulnerability
- **THEN** the project acknowledges receipt within the published window

#### Scenario: Fix coordinated
- **WHEN** a valid vulnerability is confirmed
- **THEN** a fix and disclosure timeline are agreed with the reporter

#### Scenario: Bounty paid
- **WHEN** a report meets the bounty criteria
- **THEN** the reward is paid according to the published scale

### Requirement: Incident response is rehearsed

The project SHALL maintain severity levels, roles, communication channels, escalation paths, and runbooks for consensus halt, key compromise, bridge exploit, data breach, and dependency compromise. A tabletop exercise MUST be run at least annually.

#### Scenario: Consensus halt
- **WHEN** consensus stops finalizing
- **THEN** the on-call follows the halt runbook and communicates status on the published channel

#### Scenario: Key compromise
- **WHEN** a validator or bridge key is suspected compromised
- **THEN** the compromise runbook rotates keys, pauses affected operations, and preserves evidence

#### Scenario: Postmortem
- **WHEN** a severity-one incident is resolved
- **THEN** a blameless postmortem with corrective actions is published within the documented window

### Requirement: Secrets are managed outside the repository

Private keys, API tokens, database credentials, and connector secrets MUST be stored in a secret manager, HSM, or KMS and MUST NOT be committed to source control. Access MUST be least-privilege and audited.

#### Scenario: Secret scan
- **WHEN** a commit contains a secret pattern
- **THEN** CI blocks the commit and the secret is rotated

#### Scenario: HSM-backed validator key
- **WHEN** a validator runs in production
- **THEN** its consensus key is held in an HSM or equivalent protected store

#### Scenario: Access audit
- **WHEN** a secret is accessed
- **THEN** the access is logged with identity and purpose
